Kernel-Power 与 ChangeFrequency 的三层归属划分接口行为确认后修订

确认 HardwareHal.dll!ChangeFrequency 的接口行为后，三层关系没变，但主链路变了：默认只用到第 1、2 层——自装 exe 直接调 Windows 标准 API 一次设定目标 Hz；厂商 DLL 退居「Direct 失败才用」的可选回退。

这次修订改了什么

图中位置旧图（确认之前）修订后
第 1 层 · Win32 API只读供电状态与刷新率还负责直接设定目标 Hz：CDS_TEST 探测后一次 ChangeDisplaySettingsEx
第 2 层 · exe 策略循环调 ChangeFrequency + Sleep(350) + 反复读回默认 Direct：一次设定 + 有界读回，无轮询、无多次闪烁
2 → 3 箭头实线「P/Invoke 调用」，画成主链路虚线「仅失败时回退」，厂商层可选
第 3 层 · 厂商组件标注「内部实现未确认」，工具必须依赖标注「行为已确认 · 非默认路径」；管家更新不再让钩子静默失效
第 2 层副标题写死旧工程目录名改为通用的「工程目录文件 + 任务定义」，与迁移后的位置解耦

接口行为摘要

  • ChangeFrequency(ref int afterHz, ref int beforeHz) 的两个引用参数是纯输出，DLL 从不读取调用者传入的值；函数没有目标 Hz 入参。
  • 按产品型号硬编码档位表（如 [60,120]、[48,60,90]、[60,120,165]），每次调用切到「比当前高的下一档」，到顶回绕最低档——这正是旧实现必须循环轮询的根因。
  • 底层用的就是标准 Win32：EnumDisplaySettingsExW 读、ChangeDisplaySettingsW(&DEVMODE, 1) 设 dmDisplayFrequency，一次到位。既然如此，工具完全可以自己一次设目标 Hz。
  • 该函数路径上未见 IPC 调用；有可见副作用是 CDS_UPDATEREGISTRY 写显示配置。
  • 三层归属判断不变：只有第 2 层是本工程产出的；第 1 层是 Windows 既有能力，第 3 层是荣耀既有组件，我们只写了「订阅」和「调用」两处接线。
接口行为观察结论，尚未做运行时实测。Direct 的端到端实际切换仍需触发一次电源切换（或手动启动任务）验证；SwitchMethod=HonorHal 可强制走回退路径。
